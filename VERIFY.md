# VERIFY — полнота «Ордикс Обследование» (полноценная версия) против кликабельного прототипа

Дата верификации: 2026-10-10 · Режим: read-only, сравнение по коду (без запуска).

Эталон: `ordiks-survey-prototype` (index.html ~7000 строк, README — 24 шага проверки, ОБЗОР_ФУНКЦИЙ — 9 разделов).
Продукт: `ordiks-survey` (Bun/Hono/Prisma/PostgreSQL + React webapp, монорепо).

## Итог одним абзацем

Backend продукта фактически **закрывает весь функциональный контур прототипа и превосходит его** (реальная авторизация, серверные роли, БД, S3-хранилище, приглашения, все 7 реестров + свои реестры с формулами и импортом, треды комментариев, визы). Провал — в **frontend-представлении**: часть API осталась без экранов (комментарии, 4 из 7 реестров аналитики, свои реестры целиком), а часть сценариев презентации прототипа (календарь интервью, гант этапов, аннотации фото, Word/PDF-оформление, глобальный поиск) не перенесена осознанно или ещё ждёт своей волны.

## Критичные пробелы (что сломает демонстрацию по 24 шагам README прототипа)

1. **Нет UI комментариев/тредов** (шаги 11, 24). API и сид готовы, но написать комментарий из интерфейса нельзя → колокольчик уведомлений показывает только сид-данные, SLA «ждём ответ» нигде не виден, обсуждение записи реестра Ф-102 недоступно (сам реестр тоже — см. п.2). Для клиента «комментирует и отвечает» из.promise CHECKLIST — невыполнимо.
2. **Свои реестры без экрана** (шаги 20, 24). Полный серверный контур (конструктор полей с формулами, статусы с цветами, bulk, импорт из Excel-вставки) и сид-реестр «Оснастка: формы и матрицы» существуют, но в webapp нет ни вкладки, ни страницы — единственная точка появления — вставка в отчёт.
3. **4 из 7 реестров аналитики без UI** (шаг 13): журнал решений, коммуникации, quick wins, базлайн-метрики — API + сид есть, вкладок нет; печать реестров отсутствует для всех.
4. **Календарь интервью отсутствует** (шаг 8): список и анкеты есть, но «Месяц/Неделя», конфликты, «Печать недели» — нет.
5. **Клиент видит все факты** (шаг 9, финал): пометки «показано» нет ни в схеме, ни в сервисе — аргумент «клиентский портал показывает только согласованное» не работает.
6. **Отчёт** (шаг 14): нет вставки AS-IS→TO-BE, диаграмм, оглавления/колонтитулов, ч/б-темы и Word-экспорта; печать есть, визы работают.
7. **Нет глобального поиска Ctrl+K, экскурсии, «Статуса недели»** (шаги 3, 1) — быстрые «вау-эффекты» прототипа.

Мелочи: 3 шаблона вместо 5; bulk только по статусу находок; «На проверке» в жизненном цикле запроса; массовые операции в списке задач.

## Рекомендации (по убыванию эффекта на демонстрацию)

1. **Волна UI для готового API** (самый дешёвый выигрыш — сервер уже всё умеет):
   - компонент треда комментариев (факты, находки, интервью, записи реестров) + отображение `needsAnswer` + блок «Ждём ответа» на дашборд + сводка виз на дашборд;
   - вкладки «Решения / Коммуникации / Quick wins / Базлайн» в AnalyticsPage (CRUD-паттерн уже есть в трёх существующих);
   - страница «Свои реестры»: конструктор полей/статусов, записи, формулы (сервер считает), импорт из текста.
2. **Флаг `shownToClient` у факта** + фильтрация в `facts-service.ts` + чекбокс в UI — закрывает «честность прав» для заказчика.
3. **Календарь недели интервью** (существующих данных хватает: `scheduledAt` + домен-цвет) и «Печать недели» через print-CSS, как в отчёте.
4. **Достройка вставок отчёта**: kind `processes` (AS-IS→TO-BE) и остальные 6 реестров — по образцу `inserts.ts`; после — SVG-диаграммы.
5. **Печать списков** (запросы «что от меня нужно», реестры) — переиспользовать `REPORT_PRINT_CSS`.
6. Решить, что осознанно **не переносится** (снапшоты/корзина/HTML-архив — уступки БД; Word-экспорт; Ctrl+K) — и зафиксировать в CHECKLIST.md, чтобы пробелы не выглядели забытыми.

## Оценка

- Backend как продуктообразующий слой: **готов на ~85%** к демо полного сценария (не хватает флагов «показано» у фактов, счётчиков ручных шагов, вложений запросов, некоторых insert-kind).
- Frontend: готов для сценария «ядро обследования» (проект → этапы → задачи → домены → интервью+гайды → факты → запросы → находки → процессы → GAP/риски/требования → отчёт с визами → приглашение заказчика → роли) — это шаги 1*, 4–6, 7*, 8*, 9*, 10, 11*, 12, 13*, 14*, 16*, 17, 19 со звёздочками-упрощениями.
- Совокупное покрытие функциональности прототипа: **≈48%** (32 [x] + 21 [~] + 36 [ ] на 89 функциональных пунктах). С учётом «готовности API под отсутствующий UI» эффективная готовность к быстрому закрытию пробелов — **≈75%**.
